## 2. プロダクト概要

**プロダクト名**: **noshi** (のし)

> 名前の由来: 日本の贈答に古くから添えられる「のし (熨斗)」を、軽やかに・正しく・続けられる形で支えるという意図。ドメインを直接示し、覚えやすく、検索性も高い。

**一言で**: 家族・親族・友人との贈答 (もらった / あげた) を AI が一元管理し、**お返し選定・次回額の判断・礼状文面** まで自動で運用するサービス。日本の贈答文化 (内祝い・お年玉・香典返し) を機械化する。

**目的**:
- **ハッカソン題目への解答**: 「人をダメにするサービスを考えよう!」というテーマに対し、表面はあたたかく便利・根本では人間関係の機微を AI に外注させるプロダクトとして提示する (詳細は §3)。
- **来場者デモ価値**: AWS Summit 2026 来場者が短時間で「贈答のしんどさが消える」感触を体感できるインタラクティブ体験。

**ハッカソン本番までの目標品質**:
β 版 — Receive / Give / Analytics 3 モジュールがそれぞれ動作し、来場者が選んで試せる。

## 3. ハッカソンテーマ整合性 / プロダクトナラティブ

> 本プロダクトはハッカソンテーマ「人をダメにするサービスを考えよう!」への解答であり、以下を **意図的に退化させる** ことが製品コンセプトの一部である。要件・設計の評価軸として参照する。
>
> **ナラティブ構造**: 表 (デモのキャッチ) はあたたかく前向き。中 (Analytics ROI ヒートマップ等) は意図的に退化を可視化する。**この看板と中身のコントラスト自体がテーマへの解答** である。

| 退化対象 | 仕組み |
|---|---|
| **記憶** | 誰から何をもらったか / 誰にいくらあげたかを、ユーザー本人が覚えなくなる |
| **判断** | 半返し / 三分返し / お年玉年齢別相場の決定をすべて AI に委譲 |
| **感謝** | 礼状・メッセージカードの文面を AI が代筆し、自分の言葉が消える |
| **マナー** | 「半返し」の意味すら知らないまま運用される |
| **人間観** | 累計ダッシュボードにより親族関係が ROI 思考で評価される |

### 3.1 デモのキャッチ (ポジティブ表現)

> 「**贈り合いをちゃんと続けられること** こそが、人とのつながりを保ち、幸せに生きていくための土台」というメッセージを軸とする。

**メインキャッチ案 (採用候補 1)**:
> **「のしを、軽やかに。関係を、ずっと。」**

**代替案 (採用候補 2)**:
> 「贈り合いを、ずっと続けられるように。」

**代替案 (採用候補 3)**:
> 「ちゃんとお返しできることが、人とのつながりを支えている。」

> ※ 最終採用は **User Stories** または **Application Design** の段階で UI コピーと併せて確定。idea.md の旧キャッチ (「礼儀、外注しました」 等) は **採用しない** が、皮肉的ナラティブの裏側として §3 に保持する。

## 5. Functional Requirements (機能要件)

機能群: **Receive / Give / Analytics / Receive↔Give 連携 / アカウント・ユーザー管理**

### 5.1 Receive モジュール (受け取り)

| ID | 要件 |
|---|---|
| FR-R1 | ご祝儀袋 / お祝いメッセージ / のし紙 などをカメラ撮影またはアップロードで取り込める |
| FR-R2 | 画像から **金額・贈り主・続柄ヒント・用途 (内祝い/出産祝い/結婚祝い等)** を構造化抽出する (OCR + マルチモーダル推論) |
| FR-R3 | 贈り主との **関係性 (続柄・親密度) を自動推定** し、ユーザーが補正可能 |
| FR-R4 | **半返し / 三分返し** などの文化ルールに基づき、お返し金額レンジを計算 |
| FR-R5 | 金額レンジに合った **お返し品候補を AI が提案** する (カテゴリ別 / 価格帯別) |
| FR-R6 | 用途に応じた **文化的締切日** (例: 出産祝いの内祝いは生後 1 ヶ月) を提示し、発注提案する |
| FR-R7 | 発注はユーザー承認をトリガに実行する (※ハッカソンでは外部 EC との実発注はモックで可、TBD-R1) |
| FR-R8 | 礼状 / メッセージカードの文面を **AI が自動生成** し、ユーザーが微修正できる |
| FR-R9 | 受領記録 (誰から / いくら / 日付 / 用途 / お返し状況) を履歴に保存 |
| FR-R10 | **内祝いの発送が承認・実行された時点で、その記録は Give 履歴にも自動連携される** (詳細 §5.4) |

### 5.2 Give モジュール (贈与)

| ID | 要件 |
|---|---|
| FR-G1 | お年玉 / お祝い / 香典 / **内祝い** など、贈った履歴を登録・管理できる |
| FR-G2 | **年齢段階に応じた相場** (例: 小学生 1,000 円 / 中学生 3,000 円 / 高校生 5,000 円 など) を提示する |
| FR-G3 | **「去年と同額」「親族間バランス」** を考慮した次回額の自動推奨 |
| FR-G4 | _(削除済 — 旧「年間予算と実績比較」、下記注を参照)_ |
| FR-G5 | 贈与イベント (誕生日 / お年玉時期 / お盆 / お中元・お歳暮) のリマインドを通知 |
| FR-G6 | **内祝いを含む贈与履歴を統合的に閲覧できる** (Receive 起点で発生した内祝いも、ユーザー起点で登録した贈与も同じ Give タイムラインに並ぶ) |
| FR-G7 | 内祝いとして登録されたレコードからは、**元となった Receive レコード (どの祝いに対するお返しか) へワンクリックで遡れる** |

> **FR-G4 削除済**: 旧「年間予算と実績比較」は User Stories 段階でユーザー判断により削除 (2026-05-10)。理由: 年間総額の文化的相場が存在せず、ユーザーが予算金額の判断基準を持てないため機能として成立しない。イベント単位の相場 (お年玉年齢別 / 半返し / 110 万円贈与税枠) は他要件 (FR-G2, FR-R4, FR-A4) で扱う。ID は欠番として保持し、後続 FR-G5〜G7 はそのまま。

### 5.3 Analytics モジュール (分析)

| ID | 要件 |
|---|---|
| FR-A1 | **人別 / 年別 / 用途別の累計総額** ダッシュボード (Receive / Give 双方を集計) |
| FR-A2 | **親族 ROI ヒートマップ** (もらった額 / あげた額の比率を可視化) |
| FR-A3 | **「あの人にはあげすぎ / 少なすぎ」警告** (バランスがしきい値を超えた場合) |
| FR-A4 | **贈与税 110 万円非課税枠** との関連通知 (ある相手への年間贈与累計が枠に近づいたら警告) |

### 5.4 Receive ↔ Give 連携 (Person Ledger)

| ID | 要件 |
|---|---|
| FR-L1 | 各 **人物 (Person)** を中核とした元帳 (ledger) を持ち、Receive (もらった) と Give (あげた) のレコードはこの人物に紐付く |
| FR-L2 | Receive で登録した「出産祝い 5 万円 from 義父」に対し、Receive モジュールから生成された内祝いは **同じ Person ノードに Give レコードとして自動追加** される |
| FR-L3 | Person 詳細画面では、Receive と Give の時系列履歴を **1 本のタイムライン** で表示する |
| FR-L4 | Analytics の集計はこの統合 ledger を参照する |
| FR-L5 | Receive レコードの「お返し済み / 未対応」状態は、対応する Give レコードの存在から自動判定される |

### 5.5 アカウント / ユーザー管理

| ID | 要件 |
|---|---|
| FR-U1 | ユーザーは **アカウント登録** ができる (TBD: メール+パスワード / ソーシャルログイン / マジックリンク / Cognito ホスト UI のどれを採用するかは Application Design で確定 — TBD-U1) |
| FR-U2 | 各アカウントの履歴データ (Person ledger / 画像 / 設定 等) は **他アカウントから完全分離** される |
| FR-U3 | ユーザーは自身のアカウントとそれに紐づくデータを **削除できる** (関連する Person / Receive / Give / 画像が全て削除される) |
| FR-U4 | **デモ用エントリ**: AWS Summit 来場者向けに、ワンタップでデモアカウントを作成し、ペルソナ事前データ (出産祝いの履歴等) が読み込まれた状態で開始できる (デモアカウントは短時間で自動失効) |
| FR-U5 | 認証セッションの有効期間 / 多要素認証 要否は NFR-1 セキュリティ要件 (§6) と整合させる |

## 6. Non-Functional Requirements (非機能要件)

> **NFR 優先順位**: Q6 で C (セキュリティ) と D (コスト効率) の 2 つが選択された。リスティング順から **NFR-1 セキュリティを最優先**、**NFR-2 コスト効率を準優先** とする。

### NFR-1: セキュリティ (最優先)
- **Security Baseline 拡張**: 強制適用 (Enabled)。
- **個人情報の取り扱い** (本プロダクト固有の重大事項):
  - 贈り主・受贈者の **氏名 / 続柄 / 金額** は機微度の高い PII。アカウント単位で暗号化保管。
  - デモアカウント (FR-U4) は **架空のペルソナデータのみ** を提供。来場者が任意で入力したデータは **デモセッション終了時に破棄** (短時間 TTL)。
  - 来場者の本物の家族データはデモ環境では収集しない。
- **画像取り扱い**:
  - ご祝儀袋・住所・氏名が写った画像は機微情報。S3 にライフサイクル設定で保管期間を制限。デモでは原則メモリ上処理 + 終了時破棄。
- **認証 / 認可**:
  - FR-U1〜U3 を満たす認証基盤が必要。
  - 他ユーザーのデータにアクセスできないことを境界 (API レイヤ + DB クエリ) で強制。
- **プロンプトインジェクション対策**: ご祝儀メッセージ内の自然言語に対する解釈時、ユーザー指示と画像内テキストを分離。
- **不適切応答防止**: 礼状文面生成時に Bedrock Guardrails 等で出力フィルタリング。
- **シークレット管理**: AWS Secrets Manager / SSM Parameter Store。
- **レート制限**: 1 アカウント / 1 IP の API 呼び出し上限。

### NFR-2: コスト効率 (準優先)
- サーバーレス / 従量課金 / オートスケール構成を優先。
- 生成 AI API は **画像入力 (マルチモーダル) を含む** ため単価が高い。Haiku 系の軽量モデルをデフォルト、複雑タスクのみ上位モデルへフォールバックする戦略を検討。
- 画像 OCR は **Bedrock Claude のマルチモーダル** か **Amazon Textract** を比較し、コストと精度のバランスで選定 (TBD-T1)。
- アイドル時の課金最小化 (デモ時間外の自動シャットダウン / オートスケール ゼロまで)。

### NFR-3: パフォーマンス (来場者体験品質)
- 画像 → 構造化抽出 → お返し提案までの **End-to-End 応答**: 10 秒以内が目標 (うち初回トークン 5 秒以内)。
- ストリーミング応答可能な部分 (礼状文面生成等) は積極的に採用。
- 同時セッション目安: 10〜30 (Application Design / NFR Design で確定)。

### NFR-4: 信頼性
- ハッカソン本番中に落ちないことが最優先。
- Bedrock 等外部 API のリトライ / タイムアウト / フォールバック (例: モデル A 失敗時にモデル B) を設計に含める。
- フロントエンド側でも空状態 / エラー状態を明示。

### NFR-5: 観測性
- CloudWatch Logs にエージェントの推論ステップ・ツール呼び出し・モデル選択を構造化ログで記録。
- アカウント識別子 (匿名化された ID) で追跡可能にする。
- 詳細なトレーシング (X-Ray 等) は NFR Design で要否判定。

### NFR-6: アクセシビリティ / 国際化
- UI 言語: 日本語のみ (β 版時点)。
- アクセシビリティ最低限 (キーボード操作 / コントラスト) を要件として保持、詳細は Application Design。

## 7. Technical Context (技術コンテキスト)

### 7.1 候補 AWS サービス (Q4=E のため要件ベースで推薦)

| 役割 | 候補サービス | 採用理由 |
|---|---|---|
| 生成 AI / エージェント基盤 | Amazon Bedrock + Bedrock AgentCore | プロジェクト環境に AgentCore MCP 整備済。エージェント (ツール呼び出し / メモリ) 機能をマネージドで利用可 |
| 画像理解 (OCR) | Bedrock Claude (マルチモーダル) または Amazon Textract | ご祝儀袋・のし・メッセージカードの読み取り。精度 vs コストで選定 (TBD-T1) |
| ガードレール | Amazon Bedrock Guardrails | 礼状文面 / お返し提案の不適切出力フィルタ |
| Web フロント配信 | AWS Amplify Hosting / S3 + CloudFront (+ WAF) | 静的配信 + WAF 連携 |
| バックエンド API | API Gateway + Lambda | サーバーレス・従量課金 |
| 状態管理 (Person ledger) | DynamoDB (オンデマンド) | Person 単位アクセスパターンに整合 |
| 画像ストア | S3 (TTL ライフサイクル) | NFR-1 に従い、画像は保管期間を制限 |
| 認証 | Amazon Cognito | FR-U1〜U3 のアカウント基盤候補。マジックリンク / SNS ログイン等を選択可 |
| シークレット管理 | AWS Secrets Manager / SSM Parameter Store | NFR-1 |
| 観測性 | CloudWatch Logs (+ X-Ray TBD) | 標準構成 |
| 通知 / リマインド | EventBridge + SES (or SNS) | FR-G5 のリマインド (デモではモック可) |

### 7.2 ドメインルールエンジン (本プロダクト固有)

- 半返し / 三分返し / 用途別文化的締切日 / 年齢別お年玉相場 / 贈与税 110 万円枠 などの **日本贈答文化ルール** を構造化したナレッジが必要。
- 実装方針候補: (a) コード内のルールテーブル (b) JSON / YAML データ + ルールエンジン (c) Bedrock のシステムプロンプト + RAG。
- 選定は Application Design で決定 (TBD-T2)。

### 7.3 フロントエンド技術スタック候補
- React + TypeScript を前提。
- フレームワーク選定 (Next.js / Vite + React Router / Remix) は Application Design で確定。
- ストリーミング UI (SSE / WebSocket) を扱える構成。

### 7.4 開発体制 (Q7=B)
- 2〜4 名のチーム開発前提。
- ユニット分割案 (例): (1) Web フロント (2) AgentCore + ルールエンジン (3) Receive 画像処理 (4) Person ledger + Analytics (5) アカウント基盤 — 最終分割は Units Generation で確定。

## 10. Quality Attributes (品質特性)

### 10.1 テスト戦略

## 14. 主要要件サマリ (Brief Summary)

- **何を作るか**: 日本の贈答文化を機械化する 生成 AI Web プロダクト **noshi**。Receive (受け取り) / Give (贈与・内祝い含む) / Analytics (分析) の 3 モジュール + Person ledger による Receive↔Give 連携 + アカウント基盤。
- **テーマ整合 (看板と中身のコントラスト)**:
  - 看板 (デモキャッチ): 「のしを、軽やかに。関係を、ずっと。」
  - 中身: 記憶 / 判断 / 感謝 / マナー / 人間観を意図的に退化させる構造 — このコントラストがハッカソンテーマへの解答。
- **品質目標**: β 版 — 3 モジュール + 連携 + アカウントが動作し、来場者が選択して 3〜5 分で体験完了。
- **最優先 NFR**: セキュリティ (PII / アカウント分離) / 準優先: コスト効率。
- **技術トーン**: Bedrock + Bedrock AgentCore + Cognito + サーバーレスバックエンド + DynamoDB (Person ledger) + React フロント。
- **チーム / 期間**: 2〜4 名 / Summit 本番までに β 版。
