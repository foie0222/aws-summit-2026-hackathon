# User Stories — noshi

> **方針**:
> - 分解アプローチ: User Journey-Based (Q2=A)
> - 粒度: 中粒、合計 23 Story (US-15 「年間予算と実績比較」をユーザー判断で削除し、後続を US-15 へリナンバー)
> - テンプレート: 日本語自然文 (Q4=C)
> - 受け入れ基準: チェックリスト形式 (Q5=B)
> - スコープ: 全機能 β 版 (Q6=D) — `β-must` / `β-should` / `β-stretch` の 3 段階で優先度を表現
> - デモ Story: 完全プリセット (Q7=A)、S1 最優先 (Q8=A)
> - 配分: 永続ユーザー : 来場者 = 20 : 3 (Q9=A 方針 — 永続中心、デモは派生最小限)
> - 倫理 / 法務 Story: 本ステージでは扱わず Application Design 以降に委ねる (Q10=C)
> - ペルソナ: P1 = タクヤ (永続ユーザー) / P2 = Summit ビジター (来場者)

> **優先度ラベルの意味**:
> - `β-must`: ハッカソン本番までに動作必須。デモ S1 関連はここ。
> - `β-should`: β 版に含めるが、S1 が先。
> - `β-stretch`: β 版を目指すが、時間切れ時は最後にカット可能。

---

## Epic 1: アカウント立ち上げ (永続ユーザー オンボーディング)

### US-01: アカウント登録 [β-should]
タクヤ は noshi を初めて使い始めるとき、メールアドレス等を使って自分専用のアカウントを作成したい。それは、家族の贈答記録という機微情報を他人と分離して安全に保管するためである。

**受け入れ基準**:
- [ ] サインアップ画面でメールアドレスとパスワード (またはマジックリンク) で登録できる
- [ ] 登録時に既存アカウントの重複チェックが行われる
- [ ] 登録完了後、本人確認 (メール認証等) を経てログインできる
- [ ] 登録時に利用規約 / プライバシーポリシーへの同意を求められる
- [ ] 認証方式の最終選定は Application Design (TBD-U1) に従う

**関連要件**: FR-U1, FR-U2, NFR-1

---

### US-02: 自分情報のセットアップ [β-should]
タクヤ は登録直後に、自分の表示名 / 連絡先住所 / 家族構成 (妻 / 子) など贈答に必要な基本情報をまとめて入力したい。それは、AI が礼状文面や住所まわりを正しく生成できるようにするためである。

**受け入れ基準**:
- [ ] 表示名、住所、家族構成 (任意) を入力できる
- [ ] 入力をスキップしてもアプリは起動する (後から編集可)
- [ ] 入力した情報はアカウントに紐付き、他アカウントから参照できない
- [ ] 機微情報 (住所等) は暗号化保管される

**関連要件**: FR-U2, NFR-1

---

### US-03: 親族・友人 (Person) の登録 [β-should]
タクヤ は使い始めの段階で、義両親 / 両親 / 親族 / 友人など主要な人物を登録したい。それは、後で贈り主・受贈者を即座に紐付けて履歴を蓄積できるようにするためである。

**受け入れ基準**:
- [ ] Person を新規追加できる (氏名、続柄、誕生日 (任意)、メモ)
- [ ] 既存 Person を編集 / 削除できる
- [ ] 登録した Person は Receive / Give フォームで選択肢として候補に出る
- [ ] 削除時、過去レコードがある場合は警告が表示される

**関連要件**: FR-L1, FR-U2

---

## Epic 2: Receive — 受け取りジャーニー

### US-04: ご祝儀の画像取り込み [β-must]
タクヤ は出産祝いを受け取ったとき、ご祝儀袋やお祝いメッセージカードをスマホで撮影してアップロードしたい。それは、内容を後から手入力する手間を省くためである。

**受け入れ基準**:
- [ ] ファイル選択 / カメラ起動の両方で画像をアップロードできる
- [ ] 1 件のレコードに複数枚の画像 (袋 / カード / 中身など) を紐付けられる
- [ ] 画像のアップロード進捗が表示される
- [ ] アップロードした画像はアカウント単位で分離して保管される

**関連要件**: FR-R1, FR-U2, NFR-1

---

### US-05: AI による構造化抽出と補正 [β-must]
タクヤ はアップロード後、AI が画像から **金額 / 贈り主 / 続柄ヒント / 用途** を抽出した結果を確認し、誤りがあれば手で補正したい。それは、誤った値が後段の半返し計算に伝播するのを防ぐためである。

**受け入れ基準**:
- [ ] AI 抽出結果 (金額・贈り主・用途・続柄推定) が表示される
- [ ] 各フィールドをユーザーが編集できる
- [ ] 既存 Person 候補 (US-03 で登録済) と一致する場合は紐付けが提案される
- [ ] AI が不確実と判定したフィールドはハイライトされる

**関連要件**: FR-R2, FR-R3

---

### US-06: 半返しレンジとお返し品候補の確認 [β-must]
タクヤ は受領内容が確定した後、半返し / 三分返しの文化ルールに沿った金額レンジと、AI が提案したお返し品候補を確認したい。それは、「いくらの何を返すか」を毎回ググらずに即決できるようにするためである。

**受け入れ基準**:
- [ ] 用途と金額に応じた半返し / 三分返しレンジが提示される
- [ ] レンジに合うお返し品候補が複数 (カテゴリ別 / 価格帯別) 提示される
- [ ] 候補を選択できる、または自分で別の品を指定できる
- [ ] レンジ計算ロジックは純粋関数として PBT (Partial) 対象になる旨が明示される

**関連要件**: FR-R4, FR-R5, Property-Based Testing (Partial)

---

### US-07: 文化的締切日の確認 [β-must]
タクヤ は受領レコードに対し、AI が用途別に算出した内祝い発送の文化的締切日 (例: 出産祝いは生後 1 ヶ月) を確認したい。それは、締切を見落として失礼がないようにするためである。

**受け入れ基準**:
- [ ] 受領レコードに対して文化的締切日が表示される
- [ ] 残日数が併記される (締切まで X 日)
- [ ] 締切が近い / 過ぎているレコードはダッシュボードで一覧化される

**関連要件**: FR-R6

---

### US-08: 礼状文面の AI 生成と微修正 [β-must]
タクヤ は内祝いを送る前に、礼状 / メッセージカードの文面を AI に生成させ、自分で軽く調整したい。それは、自分の言葉で書く負担を減らしつつ、相手に応じた文面にするためである。

**受け入れ基準**:
- [ ] 受領内容と贈り主との関係性に応じた文面が生成される
- [ ] 生成中はストリーミングで表示される
- [ ] ユーザーが文面を編集できる
- [ ] 生成済み文面はレコードに保存される
- [ ] Bedrock Guardrails 等による不適切表現フィルタが効く (詳細は Application Design)

**関連要件**: FR-R8, NFR-1

---

### US-09: 内祝い承認 → 発送 → Give 履歴連携 [β-must]
タクヤ は内祝いの内容と文面を確認した後、ワンクリックで発送承認したい。それは、承認した瞬間に発送 (またはモック発送) と Give 履歴への記録が自動で完了し、対応漏れがゼロになるためである。

**受け入れ基準**:
- [ ] 「発送承認」ボタンで発送処理 (本物 or モック、TBD-R1) が起動する
- [ ] 承認時刻 / 発送方法 / 金額が Receive レコードに記録される
- [ ] 同じ内容が Give 履歴にも自動的に追加される (二重入力不要)
- [ ] Receive レコードのステータスが「お返し済み」に変わる
- [ ] 発送方法 (画面表示 / メール / 郵送モック) は TBD-R2 で確定

**関連要件**: FR-R7, FR-R9, FR-R10, FR-L2, FR-L5

## Epic 3: Person ledger — 連携ビュー

### US-10: Person 詳細での統合タイムライン [β-must]
タクヤ は特定の Person (例: 義父) のページを開くと、その人との Receive (もらった) / Give (あげた) を **時系列の 1 本のタイムライン** として一覧したい。それは、その人との関係性を一目で把握するためである。

**受け入れ基準**:
- [ ] Person 詳細画面に Receive / Give が時系列で並ぶ
- [ ] 各レコードに種別 (Receive / Give)・金額・用途・日付が表示される
- [ ] レコードクリックで詳細にジャンプする
- [ ] フィルタ (種別 / 期間) が適用できる

**関連要件**: FR-L3, FR-G6

---

### US-11: お返し済み / 未対応の俯瞰 [β-should]
タクヤ はホーム画面で「お返し未対応の Receive」を一覧で確認したい。それは、対応漏れを毎日ゼロベースで思い出さずに済むためである。

**受け入れ基準**:
- [ ] ホーム画面に「未対応 Receive」セクションがある
- [ ] 各行に贈り主 / 金額 / 用途 / 残締切日数が表示される
- [ ] 行から US-06 のお返し提案画面に遷移できる
- [ ] お返し済み / 未対応の判定は対応 Give レコードの存在から自動算出される

**関連要件**: FR-L5, FR-R6

---

## Epic 4: Give — 贈与ジャーニー

### US-12: 贈与の手動登録 (お年玉 / 香典 / お祝い) [β-should]
タクヤ は内祝い以外で自分から贈った金額・品物 (お年玉 / 香典 / 結婚祝いなど) を手動で登録したい。それは、Receive 起点でない贈与も同じ Give 履歴に蓄積し、Analytics で正しく集計されるようにするためである。

**受け入れ基準**:
- [ ] 受贈者 (Person)・金額・用途・日付・品物 (任意) を入力できる
- [ ] 受贈者は既存 Person から選択する
- [ ] 入力後、対応する Person のタイムラインに即座に表示される
- [ ] 用途種別には お年玉 / 香典 / 結婚祝い / 出産祝い / その他 が含まれる

**関連要件**: FR-G1

---

### US-13: 内祝いから元 Receive への遡り [β-should]
タクヤ は Give タイムラインで内祝いレコードを見ているとき、「これはどの Receive に対するお返しか」をワンクリックで元の Receive レコードへ遡りたい。それは、お返しの背景 (誰からどんな祝いをもらったか) を即座に思い出すためである。

**受け入れ基準**:
- [ ] Receive 起点の Give レコードには「元の Receive を見る」リンクが表示される
- [ ] リンクから元の Receive レコード詳細にジャンプできる
- [ ] 手動登録した Give レコードにはこのリンクが表示されない

**関連要件**: FR-G7, FR-L2

---

### US-14: 年齢別相場 + 親族間バランスでの次回額推奨 [β-should]
タクヤ は次のお年玉や贈与イベントの前に、AI が「過去の同イベントとの整合 / 年齢別相場 / 親族間バランス」を考慮した推奨額を提示してほしい。それは、考えずに決めても親族間で不公平が起きないようにするためである。

**受け入れ基準**:
- [ ] 受贈者の年齢段階 (小学生 / 中学生 / 高校生 / 大学生 / 大人 など) に応じた相場が提示される
- [ ] 「去年と同額」「親族間バランス」を加味した推奨額が表示される
- [ ] 推奨額の根拠 (過去履歴 / バランス計算) を確認できる
- [ ] 推奨ロジックは純粋関数として PBT (Partial) 対象になる

**関連要件**: FR-G2, FR-G3, Property-Based Testing (Partial)

---

### US-15: 贈答イベントのリマインド受信 [β-stretch]
タクヤ は誕生日 / お年玉時期 / お盆 / お中元・お歳暮など、贈答イベントが近づいたときに事前リマインドを受け取りたい。それは、慌てて準備せずに余裕を持って対応するためである。

**受け入れ基準**:
- [ ] イベント発生 N 日前にリマインドが通知される
- [ ] 通知手段 (アプリ内 / メール / プッシュ) は最低 1 つ動作する
- [ ] リマインドの ON/OFF / リードタイムをユーザーが設定できる
- [ ] β 版では一部モックでも可 (TBD: 通知実装方式)

**関連要件**: FR-G5

---

## Epic 5: Analytics — 分析ジャーニー

### US-16: 累計総額ダッシュボード [β-should]
タクヤ はダッシュボードで、人別 / 年別 / 用途別の累計総額 (Receive / Give 両方) を見たい。それは、過去の贈答状況を俯瞰して関係性を把握するためである。

**受け入れ基準**:
- [ ] 人別 / 年別 / 用途別の累計が切り替えて閲覧できる
- [ ] Receive / Give をそれぞれ、または合算で見られる
- [ ] グラフ (棒 / 円) と表が併記される

**関連要件**: FR-A1

---

### US-17: 親族 ROI ヒートマップ [β-must]
タクヤ は親族 ROI ヒートマップを開き、「もらった額 / あげた額」の比率を 1 画面で確認したい。それは、(本プロダクトのテーマである) 関係を ROI で評価する皮肉的な体験を、看板のポジティブキャッチとのコントラストで成立させるためである。

**受け入れ基準**:
- [ ] 全 Person を行、用途を列とするヒートマップが表示される (またはこれに準ずる可視化)
- [ ] セルの色濃度が比率を表す
- [ ] セルクリックで Person 詳細 (US-10) にジャンプする
- [ ] β 版では永続ユーザーアカウント / デモアカウント の両方で動作する

**関連要件**: FR-A2

---

### US-18: あげすぎ / 少なすぎ警告 [β-should]
タクヤ はある相手とのバランスが大きく崩れたとき (例: 受贈額が贈与額の 3 倍を超えるなど)、ダッシュボード上で警告を見たい。それは、不公平な関係を意識的にメンテナンスするためである。

**受け入れ基準**:
- [ ] しきい値はデフォルト値が設定されている
- [ ] しきい値を超えた Person はダッシュボードでハイライトされる
- [ ] 警告の根拠 (倍率 / 累計値) が表示される

**関連要件**: FR-A3

---

### US-19: 贈与税 110 万円枠通知 [β-should]
タクヤ はある相手への 1 年間の贈与累計が、贈与税の 110 万円非課税枠に近づいたとき通知を受けたい。それは、税務上の予期せぬ事態を避けるためである。

**受け入れ基準**:
- [ ] 1 暦年単位で Person 別の贈与累計を集計する
- [ ] 累計が 110 万円の N% (例: 80%) を超えたら警告表示
- [ ] 通知文に「税理士相談を推奨」の旨が含まれる (詳細文言は TBD-L1、Application Design で確定)

**関連要件**: FR-A4

## Epic 6: 設定・データ管理

### US-20: アカウントとデータの削除 [β-should]
タクヤ は noshi の利用を止めるとき、自分のアカウントと、それに紐付く全データ (Person / Receive / Give / 画像) を一括削除したい。それは、家族の機微情報を残さず安全に撤退するためである。

**受け入れ基準**:
- [ ] 設定画面に「アカウント削除」がある
- [ ] 削除前に二段階確認が要求される
- [ ] 削除後、Person / Receive / Give / アップロード画像 が全てパージされる
- [ ] 他アカウントには一切影響しないことが保証される

**関連要件**: FR-U3, NFR-1

## Epic 7: 来場者デモ (Summit ビジター向け、3 Story)

### US-21: デモアカウント自動ログイン [β-must]
Summit ビジター はブースのデバイスで noshi を開いたとき、何の操作もなくタクヤとしてプリセットされたデモアカウントに自動ログインしたい。それは、3〜5 分の限られた接触時間でアカウント登録の手間を排除し、すぐに体験に入るためである。

**受け入れ基準**:
- [ ] ブースデバイスのセッションは事前作成済みデモアカウントに自動ログインされる (Q7=A)
- [ ] デモアカウントには事前に Person・過去 Receive・過去 Give が投入されている
- [ ] 来場者がデモアカウント上で行った変更はセッション終了 (短時間 TTL) で破棄される
- [ ] 他デバイス / 他来場者から、過去来場者の入力データが見えないことを保証する

**関連要件**: FR-U4, NFR-1

---

### US-22: デモシナリオ S1 — 義両親への内祝い [β-must]
Summit ビジター はブースで、「義父からの出産祝い 5 万円」のサンプル画像を取り込み、AI が金額抽出 → 関係性推定 → 半返しレンジ → お返し品候補 → 礼状文面 を提示し、最後に「発送承認」を押すと Give タイムラインに記録される一連の流れを 3 分で体験したい。それは、noshi の中核価値である Receive ↔ Give 連携を、最短で理解するためである。

**受け入れ基準**:
- [ ] サンプル画像をワンタップで読み込める (撮影なしでも可)
- [ ] AI 抽出 → 提案 → 礼状生成 → 発送承認 までを 3 分以内で完走できる
- [ ] 発送承認後、Person 詳細タイムラインに Receive と Give が並んでいる様子が表示される
- [ ] デモ終了画面でメインキャッチ「のしを、軽やかに。関係を、ずっと。」が表示される

**関連要件**: FR-R1〜R10 (主要), FR-L2, FR-L3

---

### US-23: デモシナリオ S2 / S3 余力枠 [β-stretch]
Summit ビジター は S1 を体験し終えた後、余力があれば S2 (来年のお年玉、いくら?) または S3 (親族 ROI ヒートマップ) を 1〜2 分で追加体験したい。それは、テーマ整合性 (退化体感) を看板のポジティブキャッチとのコントラストで掴むためである。

**受け入れ基準**:
- [ ] S1 完了画面から S2 / S3 のいずれかへ 1 タップで遷移できる
- [ ] S2 ではプリセットされた過去お年玉履歴に対して、来年の推奨額が即座に提示される
- [ ] S3 では Analytics ROI ヒートマップが事前データで描画される
- [ ] β-stretch ラベル: 時間切れ時はカット可

**関連要件**: FR-G2, FR-G3, FR-A1, FR-A2
